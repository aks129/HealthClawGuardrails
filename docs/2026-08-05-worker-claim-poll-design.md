# Worker claim-poll design (#341, task E9)

**Status:** design approved for implementation, one Dev PR.
**Decision:** ship **idle backoff with reset-on-claim** in `careagents/worker.py`.
**Long-polling the claim endpoint is BLOCKED** for the Aug 18 window. The
conditions that would unblock it are in §3.3.

The claim endpoint (`r6/agent_runs/routes.py:220`) and its service
(`r6/agent_runs/service.py:306` `claim_next`) **do not change**. That is the
central property of this design: the durable-run guarantees in
`docs/runbooks/careagents-durable-worker.md` are guarantees of the queue
transaction, and this PR does not touch the queue transaction. It changes how
often a worker asks.

---

## 1. What the poll actually costs, measured

### 1.1 The numbers that are solid

From #341, against the **HealthClawGuardrails** (engine) service:

```
railway logs --service HealthClawGuardrails -n 5000 \
  | grep -c '"path": "/command-center/api/runs/claim"'
5000
```

5000 of 5000 lines, spanning 11 min 37 s: **~7.2 requests/second, ~620k/day**,
every one `204 No Content`.

That rate is exactly what the code predicts. `CARE_RUN_WORKERS` defaults to 4
and `CARE_RUN_POLL_SECONDS` to 0.5 (`careagents/config.py:109-110`); each slot
in `run_worker_pool` sleeps `run_poll_seconds` only when it claims nothing
(`careagents/worker.py:430-431`). Four slots at a 0.5 s sleep plus ~55 ms of
request time gives `4 / 0.555 = 7.2/s`. The measurement and the code agree to
two significant figures.

Every one of those requests writes exactly one log line, because
`main.py:303-323` is a hand-rolled access log registered as `after_request` for
every path except `/static`. It logs method, path, status, duration, tenant_id
and agent_id at INFO, unconditionally, with no sampling and no level
discrimination between a 204 no-op and a 500.

So: **the poll is ~100% of the engine's log volume, and the mechanism is one
unconditional access log line per empty claim.** Retention is a line budget,
not a time budget — 5000 lines happens to be 11 minutes at this rate.

### 1.2 Where the second symptom actually lives, and what it does not show

The 502 sample in the #341 comment is from a **different service**, the
`careagents-worker`, and it does not support the conclusion drawn from it.

```
railway logs --service careagents-worker -n 2000 | wc -l   # 43
grep -c 'run claim failed (502)'                           # 24
```

43 lines is the worker's **entire log since container start**. A successful
poll logs nothing at all: `run_once` returns `False` silently on a 204, and the
only line the loop can emit is `logger.error("run claim failed: %s", exc)` at
`careagents/worker.py:428`. So the worker's log is, by construction, a log of
nothing but failures. "24 of 43 lines are 502s" says the failure log contains
failures. It says nothing about a rate.

The rate is bounded from the other direction, and it is small:

- At 7.2 req/s, a container up for even one hour has issued ~26,000 claims.
  24 failures against that is **~0.1%**.
- A 55% failure rate is arithmetically impossible against the observed cadence.
  Failed requests return faster than successful ones, so the measured rate
  would be *higher* than 7.2/s, not equal to it; and 55% of 7.2/s is 4 error
  lines per second, which would be tens of thousands of worker log lines, not
  24.

**Therefore the premise "the app is spending its capacity serving its own idle
worker" is not established by this data, and the conclusion drawn from it —
that cutting request volume addresses saturation — is not supported.** The
engine answers claims in ~55 ms at 7.2/s across 2 gunicorn workers. That is
roughly 20% utilisation of one worker. There is no saturation visible in these
numbers.

This matters because it is the whole argument for long-poll. Remove it and
long-poll is buying one thing only: fewer log lines. Backoff buys the same
thing for a fraction of the risk.

### 1.3 The 502s are a separate defect, and probably two of them

**Defect A — most likely benign, and cheap to confirm.** A 502 is generated by
Railway's edge, not by Flask; it means the edge could not get a response from
the container. Pushing `main` auto-deploys the engine. Each redeploy gives a
window of seconds where the edge has no healthy upstream, and at 7.2 req/s a
five-second window produces ~35 failed claims. **24 502s is a few deploys.**
Confirm by correlating the 502 timestamps against engine deployment times.

**Defect B — not benign, and it is hiding inside the noise.** If a 502 is
returned *after* `claim_next` committed, HealthClaw has a run in `running` with
`worker_id` set and a 60-second lease, and no worker is executing it. The
worker saw an exception and moved on. Nothing recovers that run until
`lease_expires_at` passes and some later `claim_next` calls
`_recover_expired_lease` (`r6/agent_runs/service.py:153`), which requeues it
with `attempt` already incremented. **Patient-visible effect: the chat hangs
for a full lease period, up to 60 seconds, and the SSE projection shows
nothing.** The founder's own note in #341 — "a 502 is indistinguishable from
'no work available'" — is exactly this, and it is worse than it reads.

`_recover_expired_lease` appends a durable event that makes this directly
countable:

```sql
-- HealthClaw DB. Non-zero without a known worker crash means claims are being
-- lost after commit.
SELECT count(*) FROM agent_run_events WHERE event_type = 'run.lease_expired';
SELECT count(*) FROM agent_runs WHERE attempt > 1;
```

**Neither defect is fixed by this PR, and neither should be.** File Defect B as
its own issue. It is a correctness bug in a failure path; this task is a log
volume task. Fixing it means making the claim call idempotent or retry-safe,
which is a claim-protocol change and does not ride along.

### 1.4 The one-minute check that falsifies this whole analysis

Run this before writing code. If it disagrees, the design is wrong and comes
back for review.

```bash
railway link --project <project-id> --environment production
timeout 60 railway logs --service HealthClawGuardrails \
  | grep -c '"path": "/command-center/api/runs/claim"'
```

Expected: **~430** (7.2/s × 60). Anything materially different means
`CARE_RUN_WORKERS` or `CARE_RUN_POLL_SECONDS` is not at its default in
production, and the arithmetic in §4 has to be redone against the real values.
Confirm flags with `railway logs --help` rather than trusting this document.

## 2. Options

### Option 1 — Long-poll: the server holds the claim until work or timeout T

**What it buys:** at T = 25 s, request volume drops from 7.2/s to ~0.16/s, a
45× cut, with *no* added latency — a queued run is dispatched the moment it
lands.

**What it costs, in this deployment specifically:**

1. **It occupies a gunicorn worker.** The engine runs
   `gunicorn main:app --workers 2 --timeout 300 --keep-alive 5`
   (`Dockerfile:29`). Two **sync** workers, no `--threads`, so the engine
   serves at most **two concurrent requests**. Four idle CareAgents slots
   holding four long-polls is 4 > 2: the engine stops answering anything else.
   Not degraded — stopped. The command centre, the demo FHIR reads, the
   webinar path and `/r6/fhir/health` all queue behind idle pollers. This is a
   self-inflicted outage of the engine, caused by the change intended to make
   the engine healthier.

   Making long-poll safe therefore requires changing the engine's concurrency
   model first (gthread or an async worker class), in a process that also runs
   5-minute Fasten NDJSON download threads under `--timeout 300`
   (`railway.toml:37-39`). That is a production-engine change, on its own PR,
   with its own load test and its own deploy, fourteen days before the webinar.

2. **The client timeout makes a naive hold worse than today.**
   `HealthClawClient.__init__` sets `timeout: float = 25.0`
   (`careagents/healthclaw.py:38`). A hold of T ≥ 25 s ends in a client-side
   `requests.Timeout`, wrapped as `HealthClawError("run claim failed", 0)` and
   logged as an error. A T = 30 long-poll would produce *more* worker error
   lines than today, not fewer.

3. **Readiness.** Worked through in §3.1. Short version: a hold of T makes
   presence look up to 2T old, and the fail-closed threshold is 30 s.

4. **Database.** Worked through in §3.2. A hold implemented as a sleep inside
   the claim transaction pins a connection and any `FOR UPDATE SKIP LOCKED`
   rows for the whole hold, and can block `heartbeat`, `expire_overdue_runs`
   and `finalize_run` — the fenced assistant-message transaction that the
   runbook names as a guarantee.

5. **Railway edge timeout.** Undocumented for this project and unmeasured. A
   held request that the edge decides to cut produces the same error line the
   change was meant to remove.

**Verdict: BLOCK.** Not because long-poll is wrong in general — it is the right
shape for a queue — but because the deployment it would land in cannot hold
requests, and the justification for taking that risk (saturation) turned out
not to be in the data.

### Option 2 — Idle backoff with reset-on-claim

Each idle slot doubles its sleep from `CARE_RUN_POLL_SECONDS` up to a cap. Any
successful claim by any slot in the process resets every slot to the floor.

**What it buys:** ~11× fewer requests and log lines at a 6 s cap (§4).

**What it costs:** latency on the first message after a quiet period, bounded
by the cap. Nothing else. No engine change, no engine deploy, no held
connections, no readiness interaction, no protocol change. Rollback is an
environment variable (§6).

The latency cost is smaller than the cap suggests. The four slots drift into
independent phase, so the expected wait for the earliest of four pollers at a
6 s period is ~1.2 s, with a 6 s tail. And because any claim resets all slots,
the cap only ever bites on the *first* message after silence — every message
inside a live conversation is served at the 0.5 s floor.

### Option 3 — Filter or drop the log line

Make `main.py:303-323` skip, sample, or downgrade the claim 204.

**What it buys:** the retention problem, immediately, with one condition.

**What it costs:** the requests keep happening, so Defect B keeps happening
invisibly and the poll stays unobservable in *both* directions — you could not
tell a healthy poll from a stopped one. It also edits the engine's shared
request log, which serves purposes far beyond this issue, on a deadline.

**Verdict: reject as the primary fix, but the underlying complaint is real.**
`log_request` looks like an audit trail and is actually a debug access log with
no level discrimination — 204 no-ops and 500s at the same INFO level. That is
the defect shape `docs/2026-08-02-retro.md` describes: a control that looks
like one thing and quietly does two. **File it. Do not fix it here.** After
this PR the claim contributes ~2,400 lines/day instead of 620k, and the
engine's request log stops being the thing that makes every other log
unreadable, which is the actual complaint in #341.

## 3. Risks specific to this codebase

These three sections are the reason long-poll is blocked rather than merely
deferred. They are written out in full because they will come back the next
time someone proposes holding a request.

### 3.1 Readiness and stale presence — the failure mode to understand

**The mechanism.** `claim_next` calls `_record_worker_presence(worker_id, now)`
at the top of the transaction (`r6/agent_runs/service.py:311`), where `now` is
stamped when the transaction *starts*. The row commits when the transaction
*ends* — including on the empty path, which commits before returning `None`
(`service.py:384-386`). The comment above that call states the invariant
plainly: presence is committed only if the queue transaction succeeds, so a
live process that cannot transact cannot keep readiness green merely by
existing. That invariant is load-bearing and must survive any change here.

Downstream: `worker_availability(max_age_seconds)` counts presence rows newer
than the cutoff (`service.py:273`); `GET /command-center/api/runs/workers/health`
returns 503 when the count is zero (`routes.py:193`); CareAgents `/healthz`
calls it on every hit and `POST /api/chat` calls it before admitting a turn,
returning `run_workers_unavailable` 503 when it fails
(`careagents/app.py:688-692`, `:1133`, `:747`). `CARE_RUN_WORKER_STALE_SECONDS`
is 30.

**Why long-poll breaks it.** Suppose the hold is implemented as "stamp
presence, then wait up to T for work." At any instant during a hold that began
at `t`, the newest *committed* presence is from the previous hold's start, at
`t - T`. Elapsed time since then, at the end of the current hold, is:

```
max observed presence age  ≈  2T + request latency
```

Against a 30 s threshold that caps the usable hold at **T < ~13 s**, which
throws away most of long-poll's advantage. And the four slots give no safety
margin here: they start together and block together, so they go stale together.

**Three ways out, and why each is worse than it looks.**

- *Raise `CARE_RUN_WORKER_STALE_SECONDS`.* This is the one to refuse outright.
  The runbook is explicit: "Never relax the check: a green `/healthz` with
  nothing draining the queue is the state the fail-closed design exists to make
  visible." Widening the window widens exactly that blind spot.
- *Loop short claim transactions inside the hold.* Each iteration commits fresh
  presence, so readiness is fine — but now the server is doing the polling
  instead of the client, holding a gunicorn worker and a DB connection to do
  it. All of §2 Option 1 cost 1 still applies, and the DB load is unchanged.
- *Decouple presence from the claim.* A separate cheap presence commit every
  ~10 s. Defensible, and arguably cleaner than today's conflation of "claim"
  and "I am alive" — but it must still be a real committed queue transaction or
  it breaks the invariant above, and it adds an endpoint plus a second loop.
  This is the right long-term shape. It is not a fourteen-days-out change.

**How the recommended design survives it: by not interacting with it at all.**
With a 6 s cap, each idle slot commits presence every ~6 s, so max presence age
is ~6 s against a 30 s threshold — 24 s of margin, better than the margin the
system already relies on elsewhere. Note that margin: when all four slots are
*busy*, presence comes only from `heartbeat` (`service.py:433`), which runs at
`max(2.0, lease_seconds / 3)` = **20 s** (`careagents/worker.py:97`), leaving
only 10 s of headroom. That tightness exists today, is not introduced here, and
is a second reason not to add anything else that delays presence writes.

**The QA test that pins this:** with the backoff at its cap and the queue idle,
`GET /command-center/api/runs/workers/health?max_age_seconds=30` must stay 200
continuously for at least five minutes. If it ever flips to 503, the cap is
wrong.

### 3.2 The claim path is `FOR UPDATE SKIP LOCKED` — what a held connection does

`claim_next` is not a cheap `SELECT`. In one transaction it upserts presence,
scans and recovers expired running leases under `with_for_update(skip_locked=True)`,
scans and fails overdue queued runs under the same, takes up to 50 candidate
ids, then per candidate locks the run row and locks the `Conversation` row that
serves as the cross-process mutex (`service.py:306-413`). That is six to ten
Postgres round trips, and the conversation-row lock is the mechanism enforcing
"only one running turn per conversation across all worker processes."

**Under a long-poll that sleeps inside the transaction:** every held request
pins one connection *and* holds those row locks for the duration. Concurrent
`heartbeat`, `expire_overdue_runs` and `finalize_run` — which is the fenced
transaction that commits the assistant message, its `agent.text` event and run
completion together — would block on the same rows. That is a guarantee-bearing
path, so this shape is not merely slow, it is unsafe. Any future long-poll
**must** be structured as short transaction → commit → sleep with the session
released → repeat.

**Under the current deployment, the pool is not the binding constraint.** The
engine configures `pool_size=10`, `pool_recycle=3600`, `pool_pre_ping=True` per
process (`main.py:367-371`) across 2 gunicorn processes, but only 2 requests
can be in flight at once, so at most 2 connections are ever in use. The engine
runs out of *workers* long before it runs out of connections. The order matters
for anyone who "fixes" the worker starvation by switching to gthread: at 16
threads, N held long-polls become N pinned connections, and the pool becomes
the next constraint. Both have to be sized together, in one deliberate change.

**Under the recommended design: no change.** Same transaction, same locks, same
short duration, just called ~11× less often.

### 3.3 Railway proxy and gunicorn occupancy

Covered in §2 Option 1, points 1, 2 and 5. Consolidated as the unblock
conditions, so this does not have to be re-derived:

**Long-poll is unblocked when all four of these hold:**

1. The engine no longer runs 2 sync gunicorn workers — a threaded or async
   worker class, sized against measured concurrent load, shipped and deployed
   on its own PR, after Aug 18.
2. The hold never spans an open DB transaction (§3.2).
3. Presence is decoupled from the hold and still committed only on a real
   queue transaction (§3.1), or the hold satisfies `2T + p99 < 30 s`.
4. Hold T, the client timeout (currently 25 s, `careagents/healthclaw.py:38`)
   and the measured Railway edge timeout are pinned in that order, with the
   hold strictly shortest.

## 4. Recommendation

Ship **exponential idle backoff with reset-on-claim**, capped at **6.0 s**.

```
interval starts at CARE_RUN_POLL_SECONDS (0.5)
empty claim   -> interval = min(interval * 2, CARE_RUN_POLL_MAX_SECONDS)
any claim by any slot in this process -> every slot resets to the floor
```

**Why 6.0 and not something rounder.** It is the smallest cap that clears E9's
order-of-magnitude gate against the measured baseline:

| | requests/s | lines/hour | reduction |
|---|---:|---:|---:|
| today (measured) | 7.2 | 25,920 | — |
| cap 5.0 s | 0.79 | 2,847 | 9.1× |
| **cap 6.0 s** | **0.66** | **2,377** | **10.9×** |
| cap 8.0 s | 0.50 | 1,786 | 14.5× |

(`4 slots / (cap + 0.055 s request time)`.)

The cap is set by *latency*, not by safety — §3.1 shows presence freshness
would tolerate ~20 s. If the gate needs more headroom, raise the cap; the
constraint is only how long a cold system may take to pick up the first
message. At 6 s with four phase-drifted slots, expect ~1.2 s typical and 6 s
worst case, and only on the first message after silence.

**Operational note for E10 and the webinar:** send one warm-up message before
going live. After that, reset-on-claim holds every slot at the 0.5 s floor for
the whole session.

**What this does not do:** it does not fix the 502s, and it does not claim to.
It reduces them ~11× because there are ~11× fewer requests, which is arithmetic,
not a fix. Defect B in §1.3 gets its own issue.

## 5. Confirmation gate

E9's gate: worker poll lines drop by an order of magnitude over a one-hour
window, measured before and after.

**The lines are in the `HealthClawGuardrails` service, not `careagents-worker`.**
Measuring the worker service would measure the 502 log, which is a different
thing (§1.2).

```bash
railway link --project <project-id> --environment production

# BEFORE — capture one hour on the current production build
timeout 3600 railway logs --service HealthClawGuardrails > /tmp/claim-before.log
grep -c '"path": "/command-center/api/runs/claim"' /tmp/claim-before.log
wc -l < /tmp/claim-before.log

# deploy (§6), then AFTER — one hour on the new build
timeout 3600 railway logs --service HealthClawGuardrails > /tmp/claim-after.log
grep -c '"path": "/command-center/api/runs/claim"' /tmp/claim-after.log
wc -l < /tmp/claim-after.log
```

**Expected output.** Before: claim count **~25,900**, and near-100% of total
lines. After: claim count **≤ 2,590**, and claim lines a minority of the total.

**Pass condition:** `after ≤ before / 10`.

**Second gate, and the one that proves the point of the issue.** Volume is a
proxy; observability is the goal. After the change, a one-hour capture must
contain non-poll lines that were previously evicted — the Fasten reaper's
`zombie job(s) found` at WARNING (`r6/fasten/reaper.py:68`) and the export
handlers at `r6/fasten/routes.py:139,152`:

```bash
grep -cE 'zombie job|fasten|ingest|webhook|reaper' /tmp/claim-after.log
```

Before this change that count is 0 (per #341). After, it must be non-zero
during any hour in which those code paths ran.

**Third gate, readiness (§3.1).** During the after-window, with the queue idle:

```bash
for i in $(seq 1 60); do
  curl -s -o /dev/null -w '%{http_code} ' https://careagents.cloud/healthz
  sleep 5
done; echo
```

Expected: sixty `200`s, no `503`. A single 503 with an idle queue means the cap
is interacting with presence freshness and the change comes back.

Run all three from the same window. Keep the before-capture — Railway's
retention will not let you go back for it.

## 6. Scope for the implementing PR

**One Dev PR. Two files plus tests plus one runbook row.**

### In scope

`careagents/config.py` (alongside `:110`)

- `CARE_RUN_POLL_MAX_SECONDS`, default `6.0`, validated `0.05 <= v <= 30` in
  the same style as the neighbouring knobs.
- Clamp: `run_poll_max_seconds = max(run_poll_seconds, run_poll_max_seconds)`.
  This is what makes the environment-variable rollback exact — set the max to
  0.5 and the interval can never grow, reproducing today's behaviour byte for
  byte with no redeploy.

`careagents/worker.py` (`run_worker_pool`, `:414-439`)

- One shared reset signal for the pool. The slots are threads in one process,
  so this is a single shared object, not coordination.
- Per-slot interval: floor on any claim (by any slot), double on empty, capped.
- **The sleep stays `stop.wait(interval)`, never `time.sleep`.** SIGTERM must
  still drain promptly; a `time.sleep(6)` would add up to six seconds to every
  shutdown and every deploy.

Tests (`tests/test_careagents.py`)

- Interval sequence over repeated empty claims: 0.5, 1, 2, 4, 6, 6, …
- A claim resets the claiming slot to the floor.
- A claim in one slot resets the *other* slots.
- `CARE_RUN_POLL_MAX_SECONDS == CARE_RUN_POLL_SECONDS` yields a constant
  interval identical to today. This is the rollback path; it needs a test.
- `stop.set()` ends the loop without waiting out a full capped interval.

Docs

- One row in the knob table at
  `docs/runbooks/careagents-durable-worker.md:52-61`.

### Explicitly out of scope

- **`r6/agent_runs/routes.py` and `r6/agent_runs/service.py`. Zero changes.**
  No engine deploy is required by this PR. If the diff touches `r6/`, the
  design was not followed.
- Long-poll, and any change to the engine's gunicorn worker class or thread
  count (§3.3 gates these).
- `main.py` `log_request` (§2 Option 3 — file separately).
- The 502 root cause and the lost-claim defect (§1.3 Defect B — file
  separately; it is a correctness bug, not a volume bug).
- `CARE_RUN_WORKER_STALE_SECONDS`, `worker_availability`, or anything else in
  the readiness path. Never as a side effect of a performance change.
- Restructuring the pool into one poller plus N executors. It would give
  another 4× for free, but it moves lease ownership identity, which is
  guarantee-bearing. Not before Aug 18.

### PHI

This design changes no log content: no line is added, removed, or reworded.
The engine's request log already records method, path, status, duration,
tenant_id and agent_id (`main.py:311-322`) — pseudonymous handles, no message
text — and stays exactly as it is. Nothing in the claim path logs message
content. **If the implementing PR finds itself editing what is logged, it has
left this design.**

### Rollout

CareAgents deploys need Eugene's explicit authorisation, and are a manual
`railway up` from a staged directory. Follow
`docs/runbooks/careagents-durable-worker.md` § "Stage the build" exactly, and
deploy **both** services from the **same** stage — the change is worker-only in
behaviour but `careagents/config.py` is shared, and the runbook's rule exists
because the two silently drifted 13 commits apart once already.

Confirm, per the runbook:

```bash
curl -s https://careagents.cloud/healthz     # 200, "run_workers": true, build == staged commit
```

Then send one chat message and confirm it is answered. Then start the
after-window capture in §5.

### Rollback

**Primary — no redeploy, seconds.** The clamp makes the knob a true off switch:

```bash
railway variables --set CARE_RUN_POLL_MAX_SECONDS=0.5 --service careagents-worker
```

The worker restarts on a variable change and comes back at a flat 0.5 s poll,
which is today's behaviour exactly.

**Secondary — redeploy the previous stage.** Re-stage at the prior commit and
`railway up` both services, same runbook.

**Trigger either one if:** `/healthz` returns 503 with an idle queue at any
point in the first hour, or first-message latency is visibly worse than the cap
predicts, or `run.lease_expired` events appear at a higher rate than before.
